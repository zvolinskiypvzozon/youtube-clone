# Безопасность

Модель угроз и меры. Документ пополняется по мере реализации функций; исходный чек-лист —
`.claude/agents/security-auditor.md`.

## Реализовано

### Инфраструктура
- Наружу публикуется только `web` (nginx). Postgres и хранилище доступны лишь в docker-сети;
  CI проверяет это по `docker compose config`.
- Секреты генерирует `scripts/gen-env.sh` (`openssl rand`, `.env` с правами 600), в git их нет.
  Существующие значения не перезаписываются; если `.env` потерян, а тома остались,
  `deploy.sh` останавливается с объяснением.
- Контейнеры api, worker, migrate, tests работают под uid 10001; код принадлежит root и доступен
  только на чтение. nginx — `nginx-unprivileged` (порт 8080).
- Образы закреплены до patch-версии, хранилище — по точному релизу.

### База данных
- Приложение (api, worker) подключается под ролью `yt_app` без SUPERUSER, CREATEDB и CREATEROLE
  и без права CREATE в схеме, ему разрешён только DML (`backend/app/db_bootstrap.py`).
  Суперпользователь `POSTGRES_USER` нужен только для миграций. Даже успешная SQL-инъекция
  не даст `COPY … TO PROGRAM` и не позволит менять схему.
- Автотесты работают с отдельной БД `<db>_test` и бакетами `yt-test-*`.

### Объектное хранилище
- Бакеты закрыты (`mc anonymous set none`): без подписи → 403.
- Приложение использует пользователя `yt-app` с политикой только на свои бакеты.
  root-учётка хранилища есть только у `storage-init`. Веб-консоль выключена.
- Хранилище отдаётся через nginx с того же origin, что и SPA, поэтому в location бакетов:
  - CSP `default-src 'none'; sandbox`: загруженный HTML/JS не выполнится в origin приложения;
  - `yt-raw` принимает только `PUT` (загрузка частей), `yt-media` — только `GET/HEAD`;
  - сырой URI обязан начинаться с имени бакета, иначе `/x/../yt-raw/` позволил бы обратиться
    к другим путям хранилища.

### HTTP
- Заголовки: CSP (строгая для SPA: `script-src 'self'`, `frame-ancestors 'none'`),
  `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`,
  `server_tokens off`. Общий набор подключается в каждый location
  (`infra/nginx/security-headers.conf`), потому что nginx не наследует `add_header`.
- `X-Forwarded-For` nginx перезаписывает адресом клиента (`$remote_addr`), а не дописывает.
  Подменить IP для приложения нельзя.
- Rate limit: проверка пароля (`/api/auth/login|register|token`) — 10 запросов/мин с IP
  (burst 10), против перебора; остальной `/api/` — 20 r/s. `/api/auth/me` в строгий лимит
  не входит: SPA вызывает его на каждой загрузке страницы.

### Аутентификация (ADR 0005)
- Пароли — argon2id (argon2-cffi, профиль RFC 9106: 64 МиБ), длина 8–128 (верхняя граница
  защищает от DoS длинными паролями, в т.ч. в форме `/token`). Хэширование в отдельном потоке,
  не больше двух одновременно на процесс: поток входов не исчерпает память.
  При входе хэш с устаревшими параметрами пересчитывается.
- Токен сессии — 256 бит (`secrets.token_urlsafe(32)`), в БД только SHA-256
  (CHECK на 32 байта). Утечка БД не даёт войти чужими сессиями.
- Cookie `session`: `HttpOnly; SameSite=Lax; Path=/`, `Secure` — через `COOKIE_SECURE=true` при HTTPS.
  Новый токен выдаётся на каждый вход и регистрацию: фиксация сессии невозможна. Прежняя
  сессия этого браузера при этом удаляется.
- Выход удаляет сессию в БД (повтор старого токена → 401) и идемпотентен. Бан проверяется
  на каждом запросе и действует мгновенно; истёкшие сессии отклоняются.
- Вход не раскрывает, существует ли пользователь: одинаковый ответ 401 и выравнивание
  времени проверкой фиктивного хэша. О бане сообщается только после верного пароля.
- CSRF, два слоя:
  1. middleware отклоняет `POST/PUT/PATCH/DELETE`, если `Origin` (схема, хост, порт) не совпадает
     с адресом запроса (покрывает и login CSRF, где сессии ещё нет);
  2. для запросов с cookie-сессией — заголовок `X-CSRF-Token` = `HMAC(SECRET_KEY, токен сессии)`
     (сравнение за постоянное время). Подложенная cookie `csrf` не помогает — сервер сверяет
     с вычисленным значением. Bearer-токен браузер сам не подставляет — для него не нужно.
- Swagger: `POST /api/auth/token` (OAuth2 password flow) выдаёт Bearer-токен. Браузерный
  `/api/auth/login` токен в теле не возвращает — он доступен только как HttpOnly-cookie.
- Ответы `/api/auth/*` — `Cache-Control: no-store`. Ошибки — единый формат `{"detail": "<строка>"}`,
  тексты IntegrityError и стектрейсы наружу не уходят.

### Роли и администрирование
- Роли `user`, `moderator`, `admin` хранятся в БД (`users.role`) и читаются **на каждом запросе**
  вместе с сессией. Повышение и понижение действуют сразу, без повторного входа.
- Проверка роли — зависимость `require_role(...)`: без входа 401, без нужной роли 403.
- Роль меняет только администратор (`PATCH /api/admin/users/{id}`). Схема запроса содержит только
  `role` (mass assignment невозможен), значение проверяется по перечислению.
- **Всегда остаётся хотя бы один администратор.** Смены ролей сериализуются транзакционной
  advisory-блокировкой, под ней заново читается роль инициатора; самопонижение запрещено.
  Два администратора, одновременно понижающие друг друга, не оставят систему без админов:
  второй запрос дождётся первого и получит 403 (детерминированный тест с двумя транзакциями).
- Служебные имена (`admin`, `root`, `moderator`, `support` и др.) нельзя зарегистрировать.
- Первый администратор создаётся при деплое (`app/bootstrap_admin.py` в сервисе `migrate`), строго:
  если `ADMIN_USERNAME` или `ADMIN_EMAIL` уже занят другим или не-административным аккаунтом,
  migrate завершается ошибкой, и деплой останавливается с объяснением. Так чужой аккаунт
  нельзя «подсунуть» под имя администратора. Повторный деплой существующего администратора
  (и его пароль) не меняет.
- Пароль администратора генерирует `gen-env.sh`, он хранится в `.env` (600). `deploy.sh` печатает
  его только если администратор создан именно в этом запуске и вывод идёт в терминал; иначе
  выводится команда, которой его можно посмотреть. Одноразовые контейнеры `migrate` и `storage-init`
  после деплоя удаляются: секреты в их окружении больше не видны через `docker inspect`.
- Ответы `/api/admin/*` — `Cache-Control: no-store` (там email пользователей).

### Загрузка видео (ADR 0004)
- Байты видео идут браузером напрямую в хранилище по presigned PUT; API их не проксирует.
- Ключ объекта задаёт сервер (`raw/{video_id}/source`), Content-Type объекта фиксирован
  (`application/octet-stream`). Клиент не пишет в чужой ключ и не выдаёт файл за HTML. Сырые
  файлы браузеру не отдаются: `/yt-raw/` принимает только PUT.
- **Размер не обойти:** длина каждой части входит в подпись ссылки, сумма частей равна заявленному
  размеру (≤ 2 ГБ). Часть другой длины хранилище отклоняет. При `complete` фактический размер
  сверяется ещё раз (вторая линия): при расхождении видео получает статус `failed`, объект
  удаляется. nginx пропускает тело не больше 17 МиБ.
- Не больше 3 видео «в работе» (загрузка или обработка) на пользователя. Проверка сериализована
  блокировкой строки канала: параллельные запросы лимит не обойдут (детерминированный тест
  с мутацией). Учёт `processing` не даёт одному пользователю занять очередь worker-а.
- complete и cancel — только владелец (чужое видео → 404), под блокировкой строки видео:
  повторный или параллельный complete → 409, дубля задачи нет.
- Брошенные загрузки: хранилище удаляет незавершённые multipart через 24 часа.
- Подписи и uploadId не попадают в access log nginx.

### Обработка видео (worker)
ffmpeg разбирает недоверенный файл — сложный парсер и десятки декодеров. Защита в глубину
(каждый пункт проверен на ffmpeg 7.1 из образа и закреплён тестом, ключевые — мутациями):
- **Белый список контейнеров** (`-format_whitelist`): mov/mp4, matroska/webm, avi, flv, mpegts,
  mpeg, ogg, asf. Плейлисты (HLS, concat), через которые ffmpeg читает другие файлы и «рисует»
  их в кадрах, отклоняются (тест: GIF вне списка → `failed`; без списка он стал бы `ready`).
- **Белый список кодеков** (`-codec_whitelist`): h264, hevc, vp8/9, av1, mpeg4, mpeg1/2, mjpeg;
  aac, mp3, opus, vorbis, ac3, flac, pcm. Меньше декодеров — меньше поверхность атаки.
- **Только протокол `file`** — никакой сети (SSRF).
- **Секреты worker-а закрыты от ffmpeg:** ffmpeg запускается с пустым окружением, а сам worker
  (PID 1 контейнера, тот же uid) выставляет `PR_SET_DUMPABLE=0`. `/proc/1/environ` и
  `/proc/1/mem` недоступны даже при выполнении кода в ffmpeg через уязвимость декодера
  (проверено: без этого секрет читается, с ним — Permission denied).
- **Лимиты ресурсов:** разрешение ≤ 4K, ≤ 16 дорожек, ≤ 120 fps (ffprobe); `-t` при транскоде
  (длительность из заголовка может лгать); потоки декодера/фильтров ограничены; таймауты
  с убийством процесса; stdout/stderr ffmpeg не копятся в памяти. Контейнер worker:
  `mem_limit: 2g`, `pids_limit: 256`, `cap_drop: ALL`, `no-new-privileges`.
- **Метаданные исходника не публикуются** (`-map_metadata -1`, `-map_chapters -1`): название,
  комментарии, GPS-координаты с телефона (тест: координаты были в исходнике, в результате нет).
- Входной файл без расширения: ffmpeg не выбирает формат по имени.
- Content-Type результатов задаёт сервер (`video/mp4`, `image/jpeg`); `/yt-media/` отдаётся
  с `nosniff` и `CSP sandbox`.
- Временные каталоги задач удаляются; остатки после SIGKILL/OOM — при старте worker.

### Просмотр видео (ADR 0006)
- **Единая политика** `app/services/policies.py`. Одно видео (карточка, поток) — только через
  `services/videos.get_viewable`: нет видео или нет прав → одинаковый 404 (тест сравнивает
  ответы для приватного и несуществующего). Каталог (лента, канал) — `listed_filter`:
  только `ready ∧ public ∧ ok`, для любого зрителя.
- Матрица 6 зрителей × 24 состояния видео для политики и 6 × 6 для эндпоинтов; мутации
  каждой проверки (политика, обход в `/stream`, фильтр ленты, канал, служебное состояние)
  роняют тесты.
- **Служебное состояние** (статус, видимость, пометка и причина модерации, причина отказа
  обработки) — только владельцу и модераторам/админам; остальным `state: null`.
- **Ссылки на файлы** — presigned GET на 15 минут, выдаются только после проверки прав,
  подписываются одним клиентом на постоянный внутренний host и отдаются относительными
  (ADR 0004, дополнение 1): Host запроса в подпись не входит, перебор Host не заставляет API
  создавать клиентов подписи (DoS из аудита, тест на 40 разных Host). Без подписи и с неверной
  подписью — 403 (проверено через nginx); Range работает (206). Плеер при истечении
  перезапрашивает `/stream` (день 5).
- Байты из `/yt-media/` — `Cache-Control: private, max-age=900` (ошибки не кэшируются):
  общие кэши не хранят, браузер — до 15 минут с момента получения. nginx сбрасывает
  `X-Forwarded-Host`/`Forwarded` к хранилищу; `MINIO_DOMAIN` не задаётся (ADR 0004, доп. 1).
- Ответы с подписанными ссылками — `Cache-Control: no-store` (не кэшируются ни браузером,
  ни прокси, и не утекают другому зрителю).
- Курсор пагинации непрозрачный; битый курсор → 400, а не 500 (включая даты на краю
  диапазона, переполняющиеся при переводе в UTC).

### Управление своими видео (ADR 0006, дополнение 2)
- `PATCH /api/videos/{id}`: только владелец (`can_manage`). Не может открыть → 404, как
  у несуществующего (тест сравнивает ответы); может открыть, но не владелец (включая
  модераторов) → 403; аноним → 401. Матрица 4 зрителя × 6 состояний, мутации каждой
  проверки роняют тесты.
- Схема правки: только `title`, `description`, `visibility`, лишние поля и явный `null` — 422
  (статус, модерацию, дату публикации через API не изменить).
- Права проверяются до блокировки строки (`FOR NO KEY UPDATE`): чужой запрос не встаёт
  в очередь на строку видео (находка аудита; тест: при занятой строке чужой PATCH сразу
  получает 403).
- Cookie-сессия — с CSRF-токеном (тест).
- Список допуска (`GET`/`POST`/`DELETE /api/videos/{id}/access`): те же права и ответы, что
  у `PATCH` (матрица 5 зрителей × 6 состояний для всех трёх методов; чужой запрос ничего не
  меняет). Права проверяются до поиска пользователя: чужое приватное видео и несуществующее
  неотличимы и при выдаче допуска.
- Допуск выдаётся по нику, а не по email: ники и так публичны (handle канала), а поиск по
  email раскрывал бы, какие адреса зарегистрированы. Формат ника проверяется схемой (как
  CHECK в БД) — невозможный ник отсекается 422 до запроса. Ответ выдачи содержит `user_id`
  (нужен для отзыва): UUID пользователя не секрет и не даёт прав.
- Записи допуска выбираются, считаются и удаляются только по своему видео (тест с общим
  пользователем в списках двух видео разных владельцев).
- Лимит 100 записей на видео считается под блокировкой строки видео (`FOR NO KEY UPDATE`,
  после проверки прав) — детерминированный тест гонки на 99 записях. Защищает от раздувания
  таблицы одним владельцем.
- После отзыва карточка и `/stream` для бывшего зрителя — 404 (тест); уже выданные ссылки
  живут до 15 минут (принятый риск ниже).

- `DELETE /api/videos/{id}`: права как у `PATCH` (матрица 5 × 6, видео и файлы целы при
  отказе), права — до любых блокировок (тест: при занятых строках чужой DELETE сразу 403),
  CSRF. Объекты хранилища удаляются только после commit — при сбое транзакции файлы живого
  видео не теряются. Остатки при сбое хранилища убирает maintenance; уборка `yt-raw` трогает
  только ключи `raw/{id}/source` без строки видео и старше порога — загрузку живого видео
  не обрывает (тест).
- `GET /api/me/videos` — только видео своего канала (`policies.owned_filter`, SQL-аналог
  `can_manage`), в том числе для модераторов и админов; чужие приватные и скрытые не попадают
  (тест), ответ `no-store`. Курсор не подписан: он задаёт только позицию keyset, а права
  определяет `owned_filter` (тест: курсор на чужое видео отдаёт только свои).
- `lock_timeout` API — 5 с: поток запросов к занятому видео не держит соединения пула
  дольше (503 + `Retry-After`), worker — 30 с (ADR 0006, доп. 3).

- Реакции (`PUT`/`DELETE /api/videos/{id}/reaction`): только тем, кто может видеть видео
  (`can_view`, ADR 0006), матрица 6 зрителей × 6 состояний; приватное чужое и несуществующее
  неотличимы (404). Блокировка строки видео — после проверки прав, и под ней права
  проверяются заново (тест: видео стало приватным, пока лайк ждал, — 404). Повтор той же
  реакции блокировку не берёт. CSRF для cookie-сессии. Реакции — ещё один источник
  блокировок строки видео (`lock_timeout` 5 с → 503); rate limit — день 6.
- Просмотры (`POST /api/videos/{id}/view`): `can_view` (404 и анониму), счётчик — атомарный
  `UPDATE` с условиями политики в самом запросе (`visible_filter` + `interactable_filter`):
  видео, ставшее приватным, пока запрос ждал блокировку, не засчитывается (тест). CSRF для
  cookie-сессии. Дедупликации нет — см. «Принятые риски».
- Реакции и новые комментарии — только к готовому и не скрытому модератором видео, для всех,
  включая владельца и staff (`policies.can_interact`, решение архитектора 2026-11-09): это
  публичное голосование, а доступ staff к скрытому — для разбора. Видящим скрытое видео —
  409 с причиной; читать комментарии — по `can_view`. Проверка повторяется под блокировкой
  (тест: видео скрыли, пока лайк ждал, — 409).
- Подписки: вход и CSRF; на свой канал — 400. Подписка не участвует в политике доступа:
  приватные видео канала подписчику не открываются (тест: по ссылке, поток, комментарии, список
  канала). Кто подписан на канал, наружу не отдаётся — только `subscribers_count`; свои
  подписки видит только сам пользователь (`/api/me/subscriptions` без параметра «чей список»;
  тест, в том числе что в OpenAPI нет эндпоинта подписчиков).
- Комментарии (ADR 0006, доп. 5): читать — `can_view` (404); писать — `can_view`, затем
  `can_interact` (409), условия политики — в самом `UPDATE comments_count` (тесты «стало
  приватным / скрыли / удалили, пока ждал»); удалять — автор или владелец видео
  (`can_delete_comment`) или staff (с записью в журнал модерации, ADR 0006 доп. 6), не
  виден — 404 неотличимо от несуществующего, виден без прав — 403. Текст 1–2000 символов после обрезки (схема + CHECK), NUL —
  422 в схеме, а не 500 из Postgres (тест). CSRF для cookie-сессии.
  **XSS:** сервер хранит и отдаёт текст комментария как есть (тест с `<img onerror>`);
  фронтенд обязан выводить его только как текст — без `dangerouslySetInnerHTML` и без
  разбора HTML/Markdown (день 7, проверка в ревью фронтенда). Rate limit на `POST` — день 6.

### Жалобы и модерация (ADR 0006, дополнение 6)
- Жалоба: вход и CSRF; `can_view` (404, неотличимо от несуществующего — тест), своё видео —
  400, не готово или скрыто — 409, повторная открытая — 409. Матрица 6 зрителей × 6
  состояний; дубли — быстрая проверка без блокировки и `ON CONFLICT` по частичному
  уникальному индексу (детерминированный тест двух запросов, прошедших быструю проверку;
  мутация «без индекса и без `ON CONFLICT`» роняет его). Схема: категория из перечисления,
  пояснение до 500, NUL — 422, лишние поля (`reporter_id`, `status`) — 422.
- **Кто пожаловался, видит только staff.** Ответ на жалобу не содержит автора; очередь
  (`GET /api/admin/reports`) — только moderator и admin (аноним 401, user и владелец видео —
  403, тест для всех статусов); владелец видит только причину скрытия (тест: карточка и «Мои
  видео» не содержат ни id, ни ника пожаловавшегося, ни текста жалобы).
- Скрытие, возврат, отклонение жалобы — только staff (`require_role(moderator, admin)`;
  матрицы 401/403/200, при отказе состояние не меняется). Причина скрытия обязательна,
  1–500 символов, NUL — 422. Каждое действие staff — в `moderation_log` (кто, что, причина,
  снимок); журнал без внешнего ключа на цель переживает её удаление.
- **Модератор не модерирует своё видео:** не видит жалобы на него в очереди (ни в каком
  статусе, и после удаления видео — по снимку handle), скрыть, вернуть, отклонить — 403 до
  блокировки строки (тесты). Иначе модератор узнал бы автора жалобы и судил бы сам себя
  (аудит, Medium). Админ может, в журнале — `own_video: true`.
- Порядок блокировок «видео → жалобы» и тесты гонок — ADR 0006 доп. 6. Повторная жалоба не
  берёт блокировку строки видео (тест: при занятой строке повтор сразу 409 — аудит шага 4,
  Medium).
- Ответы `/api/admin/*` — `no-store`.
- Удаление комментария staff — без причины (`DELETE` без тела): в журнал пишется снимок текста
  комментария, автор и видео — этого достаточно для разбора (аудит, Low; решение 2026-11-10).

### Плейлисты (ADR 0006, дополнение 7)
- **Приватный плейлист видит только владелец** — staff тоже 404 (модерации плейлистов нет,
  решение 2026-11-10). Отказ неотличим от несуществующего плейлиста (тест). Матрица
  5 зрителей × 3 видимости для карточки и состава; управление (правка, удаление, добавление
  и удаление видео) — матрица 4 чужих зрителя × 3 видимости × 4 действия: аноним 401,
  не может открыть 404, может — 403, состояние не меняется.
- **Состав, `video_count` и превью — по `visible_filter` текущего зрителя**, не владельца
  плейлиста: матрица 6 зрителей × 24 состояния видео (тест с пагинацией). Недоступное видео
  не показывается совсем и не учитывается в счётчике и превью (тест: первым в плейлисте стоит
  приватное готовое видео с превью — постороннему превью его не раскрывает). Отзыв допуска,
  смена видимости и скрытие модератором действуют сразу (тесты).
- **Только свои видео:** чужое, которое зритель видит, → 403, не видит (приватное, скрытое,
  несуществующее) → 404; staff тоже только своё (тест). Условие «видео этого канала»
  продублировано в блокировке строки видео.
- Видимость плейлиста в ответах — только владельцу. Страница канала — только `public`.
- Название 1–150 после обрезки, описание до 5000, NUL — 422, лишние поля — 422. Лимиты: 200
  плейлистов на канал и 5000 видео в плейлисте — под блокировкой (тесты гонок на границе).
  Битый курсор (в том числе позиция вне `integer`) — 400, а не 500.

## Запланировано (дни 2–6)
- Presigned PUT с подписанным `Content-Type` и коротким TTL; проверка размера в API (2 ГБ)
  и worker (фактический размер, ffprobe, ≤ 60 мин); ffmpeg без shell, с таймаутом.
- Бан пользователя (день 6, шаг 3).

## Принятые риски

| Риск | Почему принят |
|---|---|
| Накрутка просмотров: без дедупликации, вход не нужен; владелец тоже засчитывает свои просмотры. До дня 6 предел — общий лимит nginx на `/api` (20 r/s с IP, burst 40). Поток просмотров создаёт очередь на строку `videos` популярного видео (до `lock_timeout` 5 с → 503). То же для `POST` комментариев (каждый держит строку видео до commit) — rate limit на них тоже день 6 | Упрощение дня 5, утверждено архитектором: счётчик просмотров — не механизм доступа, данные не раскрываются. День 6 — `limit_req` на изменяющие запросы; дальше — дедупликация и вынос счётчиков из строки `videos` |
| `DELETE /api/comments/{id}`: несуществующий комментарий отвечает 404 одним запросом, существующий под невидимым видео — двумя (проверка `can_view`); по задержке теоретически видно, что комментарий существует | id — случайные UUID, получить их можно только из выдачи, доступной тому, кто видео видит; текст и код ответа одинаковые (аудит шага 2, Low) |
| Комментарии из одних невидимых символов (U+200B) и с bidi-override (U+202E) проходят валидацию: «пустые» комментарии, подмена направления текста. То же — в пояснении к жалобе и причине модерации (видны staff и владельцу) | Не XSS: вывод — только текстом. Фильтр — день 6, шаг 1 (решение архитектора 2026-11-10 для комментариев, названия и описания; пояснение жалобы — решение на шаге 1) |
| Поток жалоб с многих аккаунтов держит `FOR SHARE` на строке видео: новые `FOR SHARE` присоединяются к уже взятым, и скрытие, правка, удаление видео, реакции и комментарии могут ждать до `lock_timeout` 5 с → 503 | Повтор от одного пользователя блокировку не берёт (быстрая проверка). Многоаккаунтный поток упирается в лимит регистрации 10/мин с IP и общий лимит `/api`; зона `limit_req` для жалоб — шаг 2 дня 6 (аудит шага 4, Medium) |
| Засорение очереди модерации: после отклонения можно сразу пожаловаться снова, потолка открытых жалоб на пользователя нет | Очередь видит только staff; rate limit — шаг 2 дня 6. Охлаждение и потолок — решение архитектора на шаге 2 (аудит шага 4, Low) |
| Запрет «модератор не модерирует своё видео» работает по аккаунту, а не по человеку: модератор может загрузить видео со второго обычного аккаунта и видеть авторов жалоб на него; два модератора могут разбирать жалобы друг на друга | Кодом не устранить. Каждое действие staff — в `moderation_log` с `actor_id`, админ может проверить журнал (аудит, Low) |
| Отзыв допуска к приватному видео, пока жалоба ждёт блокировку строки видео, не учитывается: `video_access` читается по снимку начала запроса | Пользователь имел доступ в момент запроса, ответ ничего не раскрывает, жалобу видит только staff. Так же устроены комментарии и просмотры (аудит шага 4, Low) |
| Поиск: короткий (1–2 символа) или ничего не находящий запрос проходит каталог по `ix_videos_feed` с проверкой `ILIKE` на каждой строке (O(N)); `statement_timeout` не задан | Утверждено: без минимальной длины. Каталог задания мал; общий лимит nginx 20 r/s с IP. День 6 — отдельная зона `limit_req` для поиска и `statement_timeout` на запросы API с ответом 503 (аудит шага 4, Low) |
| Поиск через триграммный индекс читает и строки не каталожных видео с совпадающим названием, затем отбрасывает их фильтром: теоретический тайминг-канал | Разница — микросекунды, на фоне сети и rate limit не измерима; ответ одинаков для всех. Строгий вариант — частичный GIN-индекс с предикатом каталога (аудит шага 4, Low) |
| Presigned URL можно переслать, до истечения TTL он работает у любого | TTL раздачи короткий, выдаётся только после проверки прав; ссылки на загрузку живут 1 час (долгая загрузка 2 ГБ), но позволяют лишь записать части с точной длиной в свою же загрузку (ADR 0004) |
| `complete` держит блокировку строки видео и соединение БД, пока хранилище склеивает части | Блокируется одна строка (complete/cancel того же видео); у пользователя не больше 3 незавершённых загрузок. Если склейка станет узким местом — двухфазный complete со статусом `completing` |
| silo внутри контейнера работает от root | Так устроен upstream-образ; хранилище не опубликовано наружу (ADR 0002) |
| `/api/health` анонимно сообщает `ok`/`fail` по БД и хранилищу | Без версий, хостов и текста ошибок; под rate limit; отдельный S3-клиент с таймаутом 2 с и без повторов, поэтому зависшее хранилище не забивает пул потоков. Нужен для `deploy.sh` и CI |
| Имена бакетов зашиты в location nginx | Короткий явный allowlist (ADR 0004) |
| Пакеты `docker-ce` из официального репозитория не закреплены по версии | Ставятся один раз на чистую ВМ, берётся актуальная стабильная версия |
| Уязвимость в декодере ffmpeg (RCE) | Остаточный риск при обработке недоверенных файлов. Ограничен: белые списки форматов и кодеков, ffmpeg без окружения, секреты worker-а закрыты `PR_SET_DUMPABLE`, контейнер без capabilities с лимитами памяти и процессов. Полная изоляция (ffmpeg в отдельном контейнере без секретов и сети) — возможное развитие |
| У worker нет лимита CPU, файловая система не read-only | Лимит CPU невозможен на ВМ с 1 vCPU (ADR 0003). Код принадлежит root и только читается uid 10001; записываемы только /tmp и домашний каталог |
| В `jobs.last_error` пишется текст исключения | Только для диагностики, через API не отдаётся. Пользователь видит `videos.failure_reason` — фиксированные строки |
| Внешние data references mov (drefs) выключены по умолчанию ffmpeg, а не явно | Опция есть только у mov-демультиплексора и ломает открытие других форматов. Версия ffmpeg закреплена образом |
| Регистрация сообщает, что email или имя заняты | Без этого пользователь не поймёт, почему не может зарегистрироваться (так делает и YouTube). Перебор ограничен rate limit 10/мин с IP |
| Cookie без `Secure` по умолчанию | По ТЗ проверка идёт по HTTP на IP; при HTTPS включается `COOKIE_SECURE=true` |
| Rate limit по IP: за NAT клиенты делят лимит; при IPv6 атакующий с /64 получает много адресов | На целевом стенде IPv4. При включении IPv6 — ключ лимита по /64 и счётчик неудачных входов на аккаунт |
| Пароль администратора один раз печатается в терминал при первом деплое | Только в TTY (не в логи CI и не через `tee`). Смена пароля появится вместе с профилем, до этого пароль хранится в `.env` (600) |
| Секреты видны через `docker compose config` / окружение работающих контейнеров | Доступ к Docker равен root на хосте. Одноразовые контейнеры с правами владельца БД и root хранилища после деплоя удаляются |
| После отзыва допуска или смены видимости уже выданная ссылка на поток работает до 15 минут, а скачанные байты остаются в кэше браузера до 15 минут с момента получения | Ссылка выдаётся только после проверки прав и живёт TTL; отзывать подписи S3 не умеет. Новые ссылки после отзыва не выдаются (404). Кэш — только приватный, браузера этого зрителя |
| Unlisted-видео в публичном плейлисте видно всем, кто откроет плейлист (`visible_filter`, ADR 0006, доп. 1 и 7) | В плейлист попадают только свои видео (ADR 0006 доп. 7), так что unlisted оказывается в открытом плейлисте только по решению самого владельца — как раздать ссылку. В каталог (лента, поиск, страница канала) unlisted не попадает. Нужна приватность — видимость `private` со списком допуска |
| Пропуски в `position` состава плейлиста (и курсор, в котором позиция) и `updated_at` плейлиста показывают постороннему, что в составе есть недоступные ему видео или что владелец менял состав (аудит шага 6, Low) | Раскрываются только факт и место, без содержимого. Пропуск неотличим от удалённого элемента, а `updated_at` — от добавления и удаления своего же видео, которое потом удалено или скрыто. Содержимое, число и превью недоступных видео не раскрываются (тесты K4) |
| Страница плейлистов канала (до 50) считает `video_count` и превью по всем элементам: до 250 тыс. строк на запрос при 5000 своих видео в каждом плейлисте (аудит и ревью шага 6, Low) | Состав — только свои видео, по одному разу: чтобы так нагрузить, нужно загрузить 5000 видео. GET-запросы ограничит rate limit (шаг 2); дальше — `LATERAL` с ограничением или кэш |
| Проверка `Origin` сравнивает с `Host` запроса, а не с allowlist | Работает за нашим nginx, который передаёт `Host` клиента без изменений. TLS-терминатор перед nginx потребует allowlist `ALLOWED_ORIGINS` |
