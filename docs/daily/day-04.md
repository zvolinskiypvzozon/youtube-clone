## Решения архитектора

- **Каталог и «видимое мне» — разные правила** (дополнение 1 к ADR 0006). Unlisted и приватное
  с допуском открываются по ссылке и видны в плейлистах, но не в ленте, поиске и на канале.
  Каталог одинаков для всех зрителей, включая владельца и модераторов.
- **Unlisted в чужом публичном плейлисте** видно его зрителям — принятый риск, как на YouTube.
- **TTL ссылок на поток — 15 минут.** Перезапрос ссылки плеером при 403 — обязательный пункт дня 5.
- Все качества — одним запросом `/stream`; удаление видео пока только владельцем
  (сервис не зависит от роли, модерация дня 6 переиспользует).
- **Просмотры** — день 5, засчитываются после нескольких секунд воспроизведения, а не по `/stream`.
- **Подпись на постоянный host** `media.internal` + относительные URL (дополнение 1 к ADR 0004)
  вместо подписи на Host запроса; `Cache-Control: private, max-age=900` для `/yt-media/`.
- Исправление подписи — отдельным `fix`-коммитом раньше эндпоинтов (чинит код дня 3);
  карточка/поток и лента/канал — одним коммитом (общий сервис).

## Проблемы и как решены

1. **DoS через перебор `Host` (High, аудит).** Подпись на Host запроса создавала клиента boto3
   на каждый новый Host: ~0,35 с CPU под общей блокировкой (замер: 10 клиентов — 3,5 с CPU).
   Путь существовал с дня 3 (загрузка, нужен вход), анонимная лента открыла его всем.
   Решение — постоянный host подписи (константа, совпадает с nginx), один клиент на процесс.
   Живой стек: 40 запросов ленты с разными Host — 1,0 с.
2. **Проверка индекса ленты сначала проверяла не то.**
   - `prepared.explain()` asyncpg конфликтует с JSON-кодеком SQLAlchemy;
   - `fetch` с `$N` без аргументов подвесил протокол asyncpg, а `TRUNCATE` в teardown ждал блокировку
     этой сессии (контейнер тестов остановлен вручную);
   - NULL в `EXPLAIN EXECUTE` planner сворачивал в константу;
   - `SET LOCAL` не действовал: SQLAlchemy открывает транзакцию лениво, на первом запросе через
     свой адаптер, а прямые вызовы драйвера её не открывают — план был custom, а не generic.

   Итог: `PREPARE` простым протоколом → `EXPLAIN EXECUTE` с литералами при
   `force_generic_plan` после явного старта транзакции (с проверкой, что она открыта).
   На настоящем generic-плане лента использует `ix_videos_feed` — литералы в `listed_filter` нужны.
3. Для канала planner на пустой статистике выбирает `ix_videos_feed` с фильтром по каналу.
   Это корректно; тест проверяет только, что `videos` читается по индексу.
4. Ложная тревога «нет `Cache-Control` через nginx»: скрипт проверки искал заголовок
   с учётом регистра. Перед выводом о дефекте — проверять сам инструмент проверки.
5. Скрипт правок упал на середине (форматтер раньше переформатировал блок) — часть правок
   применилась. Проверено по `git diff`/`grep`, остальное доприменено.

## Ревью и аудит

| Шаг | Находка | Серьёзность | Исправление |

| 1 | Константы SQL собирались функцией из f-строки | Low | Модульные константы-литералы |
| 1 | `visible_filter` можно по ошибке вызвать от владельца плейлиста | Low | Докстринг: аргумент — текущий зритель |

| 2 | Signing host настраивался из env, а в nginx — константа | Low | Константа `SIGNING_HOST` |
| 2 | `zip(strict=False)`, связь роутов, пробелы тестов (ready без транскодов, `no-store` канала) | Low | Исправлено |
