## Решения архитектора (2026-11-10)

- **Порядок дня:** сначала нужное фронтенду — 4, 6, затем 3, 2, 1, 7; что не успели до 16:00 —
  на утро дня 7.
- **Видео забаненного** — 404 для всех, включая прямую ссылку и допуск; staff видит для разбора.
- **Лимиты** (по IP): `write` 5 r/s burst 20, `views` 30 r/m burst 10, `comments` 10 r/m
  burst 5, `search` 5 r/s burst 10; `statement_timeout` API — 5 с. Шаг smoke с 429 — последним.
- **Бан:** модератор банит только пользователей; админ — пользователей и модераторов; админа
  через API не забанить, себя тоже. Тест на каждый запрет и мутация.
- **Удаление пользователя** — день 9. **Swagger без CDN и образы по хэшу** — день 9 (вместе
  с Actions по хэшу). **Debounce поиска** — день 7 (фронтенд).
- **Жалобы:** категория (`spam`, `violence`, `adult`, `copyright`, `other`) + необязательное
  пояснение. Владелец видео не видит, кто пожаловался, — только причину скрытия; жалобы видит
  только staff. При отмене скрытия закрытые жалобы **не открываются** — историю фиксирует
  журнал. Порядок блокировок «видео → жалобы» при скрытии и при удалении видео (`SET NULL`)
  проверить и записать в ADR.
- **Модератор и своё видео:** модератор не скрывает и не возвращает своё видео, не отклоняет
  жалобы на него (403) и не видит их в очереди — иначе узнал бы автора жалобы. **Админу
  можно**, действие пишется в журнал (`own_video: true`). Тесты на каждый запрет, мутация
  «без проверки владельца».
- **Отложено до шагов 2 и 1:** лимит на жалобы (охлаждение после отклонения, потолок открытых
  жалоб) и фильтр символов в пояснении к жалобе.

## Шаг 4 — жалобы и модерация

**Схема** (`a054d39`, миграция `3c6f18f885c5`): `reports` — снимок видео (название, handle
канала), `video_id` → `SET NULL` при удалении видео, частичный уникальный индекс «одна
открытая жалоба пользователя на видео», CHECK «закрыта ⇔ `resolved_at`»; `moderation_log` —
действие staff, цель без внешнего ключа (переживает удаление), снимок в `jsonb`. Индекс
`ix_reports_video` для `SET NULL` добавлен после самопроверки: частичный индекс покрывает
только открытые жалобы.

**Жалоба** (`2cbe620`): `POST /api/videos/{id}/reports` — `can_view` → 404, своё видео → 400,
не готово или скрыто → 409, повтор → 409. Строка видео `FOR SHARE` с условиями политики
в самом запросе; снимок берётся под блокировкой. Автор жалобы в ответ не попадает.

**Модерация**: `GET /api/admin/reports` (очередь, keyset), `PUT
/api/admin/videos/{id}/moderation` (скрыть с обязательной причиной / вернуть),
`POST /api/admin/reports/{id}/dismiss`, удаление чужого комментария staff через
`DELETE /api/comments/{id}`. Все действия — в `moderation_log`. Роль staff — из
`policies.STAFF_ROLES`, правило «своё видео» — `policies.can_moderate`
и `moderation_queue_filter`, проверка до блокировки строки видео.

**Порядок блокировок «видео → жалобы»** (ADR 0006 доп. 6), тесты гонок:
- жалоба держит `FOR SHARE`, скрытие ждёт и после её commit закрывает и её;
- скрытие держит строку, жалоба ждёт и получает 404 (user) / 409 (модератор);
- отклонение ждёт удаление видео и отклоняет жалобу с `video_id = NULL`;
- отклонение во время скрытия — 409 (жалоба уже `resolved`).

Взаимоблокировку при обратном порядке (жалоба → видео) тест не воспроизводит — порядок
закреплён кодом и ревью (записано в ADR).

### Проверки

- Жалобы (до коммита `2cbe620`): pytest **602 passed**; мутации **9 из 9** ловятся
  (применение — `diff -r`), в том числе «без индекса и без `ON CONFLICT`» — после добавления
  детерминированного теста двух запросов, прошедших быструю проверку.
- Модерация: полный pytest **655 passed**; мутации — **19**, применение каждой проверено
  `diff` (2–9 строк). Ловятся 16; 3 не ловятся из-за продублированной защиты, и для каждой
  мутация обоих мест ловится:
  - скрытие без блокировки видео — ждёт жалобу на неявной блокировке `UPDATE videos` при
    autoflush; вместе с переносом закрытия жалоб до изменения строки — падает обратный тест
    порядка блокировок;
  - роль staff проверяется в роуте (`require_role`) и в `policies.can_moderate` — мутации
    «без роли» для скрытия и отклонения проходят; двойные (роут + `can_moderate`) — падают
    тесты «только staff» для user.
  Остальные: очередь без роли, скрытие без закрытия жалоб, отклонение без условия «открыта»,
  staff без права удаления комментария, удаление без журнала, `can_moderate` без проверки
  владельца, проверка владельца убрана из скрытия / из отклонения / перенесена после
  блокировки, фильтр очереди убран / без ветки удалённого видео / только для открытых,
  «409 раньше 403».
- Обрыв WSL посреди прогона мутаций стёр `/tmp` (логи и скрипт мутаций). Рабочее дерево не
  пострадало; скрипт восстановлен, 6 готовых мутаций не перезапускались (результаты были
  прочитаны до обрыва), остальные 13 — с логами в `~/.cache/yt-clone-mutations`.
- ruff чистый; миграция `upgrade → downgrade → upgrade` на dev-БД и на пустой `yt_test`,
  `alembic check` без расхождений.

### Ревью и аудит

- **Жалобы:** ревью APPROVE (условие — ADR 0006 доп. 6); аудит: Medium — поток повторных
  жалоб держал `FOR SHARE` на строке видео и мешал скрытию → быстрая проверка повтора без
  блокировки, тест «при занятой строке повтор сразу 409». Low — в принятые риски
  (многоаккаунтный поток до rate limit, засорение очереди, отзыв допуска во время ожидания).
- **Модерация:** ревью APPROVE — исправлено: журнал удаления комментария только для staff,
  роли staff из одного места, `scalar_one` для handle, тесты (CSRF, 422 отклонения, причина
  возврата только в журнал, приватное видео в очереди, `processing` → `ready` остаётся скрытым).
  Аудит: Medium — модератор-владелец видео видел авторов жалоб на себя и мог вернуть своё
  видео → решение архитектора «модератор не модерирует своё видео», реализовано.
- **Правка «своё видео»:** ревью APPROVE, аудит — Critical/High/Medium нет. Исправлено:
  тест очереди проверял пустые статусы (`resolved`/`dismissed`) — теперь жалобы во всех
  статусах; тест «403 раньше 409» по закрытой жалобе на своё видео; журнал при отказе по
  удалённому видео; `own_video` при возврате админом.

### Принятые риски шага (`security.md`)

- **Запрет «своё видео» — по аккаунту, а не по человеку:** модератор может загрузить видео со
  второго обычного аккаунта и видеть авторов жалоб на него; два модератора могут разбирать
  жалобы друг на друга. Кодом не устранить; каждое действие staff — в журнале с `actor_id`.
- Поток жалоб с многих аккаунтов держит `FOR SHARE` на строке видео (до rate limit шага 2).
- Засорение очереди повторными жалобами после отклонения (решение — на шаге 2).
- Отзыв допуска во время ожидания блокировки не учитывается (как у комментариев и просмотров).
- Невидимые и bidi-символы в пояснении к жалобе и причине модерации (решение — на шаге 1).

### Отложено из аудита

- CHECK на `videos.moderation_reason` (≤ 500, «причина ⇔ скрыто») — шаг 3 (бан пишет в те же
  поля, одна миграция).
- Смена роли в журнал модерации (`role_change`, значение enum) — шаг 3, вместе с баном.
- Причина при удалении комментария staff — не добавляется (в журнале снимок текста;
  `security.md`).

## Шаг 6 — плейлисты

**Решения архитектора (2026-11-10):** приватный плейлист видит только владелец — staff тоже
нет (модерации плейлистов нет); в плейлист — только свои видео, чужие в перенос не вносятся;
лимиты 200 плейлистов на канал и 5000 видео в плейлисте; страница канала — только public,
свои — `/api/me/playlists`; фильтр невидимых символов для названия и описания — на шаге 1;
пропуски `position` и `updated_at` — принятый риск.

**Схема** (`ed7c320`, миграция `020f33bca74b`): `playlists`, `playlist_items` (PK
`(playlist_id, video_id)`, `UNIQUE (playlist_id, position)`, индекс по `video_id` для каскада).
Счётчика видео нет — бан и удаление пользователя ничего не пересчитывают.

**API** (`e277481`): 8 эндпоинтов. Состав, `video_count` и превью — `visible_filter` текущего
зрителя; управление — 401 / 404 / 403 (ADR 0006 доп. 2); чужое видео — 403 (видит) или 404.
Порядок блокировок «канал → count → insert» и «плейлист → видео (`FOR KEY SHARE`) → insert»,
удаление видео строк плейлистов не блокирует (ADR 0006 доп. 7, `6f84dab`). Битый курсор —
400 с общим текстом, как у ленты, поиска и комментариев.

### Проверки

- Полный pytest — **787 passed**; ruff чистый; фронт собирается; стек поднят, `/api/health`
  200, рабочая БД на `020f33bca74b`. После ревью добавлено 7 тестов, после уточнения
  архитектора — проверка текста ошибки курсора (тесты курсора зелёные).
- Мутации — **16 вариантов 12 мутаций плана, ловятся все**, применение каждой — `diff`
  (1–6 строк). Защита продублирована в «только своё видео» (условие канала под блокировкой):
  одиночная мутация ловится по 404 вместо 403, двойная — по добавлению чужого видео. Без
  `FOR KEY SHARE` тест «удаление ждёт добавление» проходит за счёт блокировки проверки внешнего
  ключа, а «добавление ждёт удаление» падает (500 вместо 404).
- Ревью — APPROVE, High/Medium нет; Low исправлены (абзац о пагинации, сравнение дат в тесте,
  недостающие тесты). Аудит — High/Medium нет; Low записаны: пропуски `position`/`updated_at`
  (принятый риск), взаимоблокировка удаления плейлиста с очисткой брошенных загрузок (503,
  ADR), стоимость списков плейлистов (шаг 2).

## Шаг 3 — бан

**Решения архитектора (2026-11-10):** модератор банит и разбанивает только user, админ —
user и moderator, админа и себя — никто, бан админа модератор не снимает; все запреты —
один код 403, повтор — 409; staff видит комментарии забаненного с пометкой `author_banned`;
`owner_id` в очереди жалоб и `author_user_id` в комментариях — только staff; перепроверка
бана под блокировкой в комментарии, реакции, подписке.

**Сделано** (`28190dd`, миграция `ef599b78e7c1`; ADR 0006 доп. 8 — `7d38fb4`):
`PUT`/`DELETE /api/admin/users/{id}/ban`; контент забаненного (видео, канал, плейлисты,
комментарии, «Мои подписки») видит только staff, staff — 409 на взаимодействие; сессии
удаляются; `recount_for_user` пересчитывает счётчики при бане и разбане; смена роли
забаненному — 409, смена роли — в журнал; CHECK бана и `moderation_reason ⇔ hidden`.

**Отклонение от плана:** перепроверка бана — блокировкой своей строки пользователя
`FOR SHARE` **до** видео или канала (тот же порядок, что у бана), а не запросом после.
Вариант «после» пропускал комментарий под видео, которого бан не касается. Подтверждено
ревью.

### Проверки

- Полный pytest — **1013 passed, 0 failed, 0 skipped**; ruff чистый; фронт собирается; стек
  пересобран, `/api/health` 200, рабочая БД на `ef599b78e7c1`.
- Мутации — **35 одиночных и 4 двойные**, применение — `diff`. Не ловятся три одиночные, все
  из-за продублированной защиты, двойные к ним ловятся: «себя забанить» (цель «себя» всегда
  с ролью инициатора, свою роль не банит никто) и 409 staff на комментарий и жалобу (условие
  ещё в `interactable_filter`).
- Ревью — CHANGES REQUESTED, аудит — Medium; исправлено: цель бана `FOR NO KEY UPDATE`
  (взаимоблокировка с проверками внешних ключей), роль инициатора — только у незабаненного,
  staff — 409 на подписку к каналу забаненного, удаление скрытого комментария — 404, вход во
  время бана — 403 без живой сессии, удалён `get_by_handle`; добавлены тесты. Принятые риски —
  в ADR и `security.md`.
- Сон компьютера оборвал запросы ревьюера и аудитора; после пробуждения оба доработали,
  перезапущенные копии остановлены.

## Шаг 2 — rate limit и `statement_timeout`

**Решения архитектора (2026-11-10):** зона `reports` 5 r/m, burst 3; потолок 20 открытых жалоб
на пользователя без охлаждения; бан и разбан — `statement_timeout` 30 с; `/stream`, `/yt-media`,
`/yt-raw` — вне зон `write` и `api`.

**Сделано** (`a52a24b`, миграция `538a0286b0f3`; docs — `b93bb1f`): зоны `write`, `views`,
`comments`, `reports`, `search` в nginx (ключ через `map`); `statement_timeout` API 5 с →
503, worker без предела, alembic — свой движок; потолок открытых жалоб под блокировкой строки
пользователя, жалобы на удалённые видео не считаются; списки плейлистов — до 20, превью через
`LATERAL … LIMIT 1`.

### Проверки

- Полный pytest — **1024 passed, 0 failed, 0 skipped**; ruff чистый; фронт собирается;
  `nginx -t`; `/api/health` 200, рабочая БД на `538a0286b0f3`.
- Мутации — **10, все ловятся** (применение — `diff`).
- `curl` по зонам: write 24/30, views 11/15, comments 6/8, reports 4/6 прошло, остальное
  429; search при 40 параллельных — 13 прошло, 27×429, и так же для `?q=&q=a` и `?%71=a`;
  лента без `q` — 40/40; `/stream` 300 при ~36 r/s — 0×429 (лента при ~25 r/s — 46×429);
  `/yt-media`, `/yt-raw` — 0×429. `SHOW statement_timeout`: api `5s`, worker `0`, alembic `0`.
- Ревью — CHANGES REQUESTED, аудит — Medium: обход зоны `search` через повторный и
  закодированный `q` — исправлено (ключ по всей строке запроса), проверено `curl`. Low
  исправлены (частичный индекс, удалённые видео в потолке, тесты бана во время жалобы и
  утечки `SET LOCAL`, `= ANY` в подсчёте) или записаны в принятые риски.
