# ADR 0002: Объектное хранилище — pgsty/silo (форк MinIO)

- Статус: принято
- Дата: 2026-11-07

## Контекст

Видео, транскоды и превью хранятся в S3-совместимом хранилище. Изначально планировался MinIO,
но на 2026-11-07 официальные образы недоступны:

- `docker manifest inspect minio/minio:latest` → `denied: requested access to the resource is denied`;
- `quay.io/minio/minio` требует авторизации;
- MinIO прекратил публикацию community-образов (2025).

Деплой должен работать на чистой Ubuntu без авторизации в реестрах.

## Решение

Используем **`pgsty/silo:RELEASE.2026-10-18T00-00-00Z`**. Это поддерживаемый форк MinIO
(проект Pigsty) с тем же S3 API и admin API; клиент `mc` есть в том же образе.

- Тег закреплён. `latest` не используем; самый свежий релиз `RELEASE.2026-10-26` моложе двух недель,
  поэтому выбран предыдущий.
- Проверено вручную 2026-11-07:
  - образ скачивается анонимно (amd64/arm64), бинарник сервера `silo`, внутри `mc` той же версии;
  - `mc ready`, `mc mb`, `mc anonymous set none`, `mc admin user add`, `mc admin policy create/attach`
    работают, повторный запуск idempotent;
  - presigned PUT/GET через nginx с сохранением `Host`: PUT → 200, GET с `Range` → 206;
    без подписи, с подменённым ключом или с чужим `Host` → 403.
- Один образ запускается и как сервер (`storage`), и как init-контейнер (`storage-init`, через `mc`).
- Приложение обращается к хранилищу **только через S3 API (boto3)** и ничего не знает о реализации.
- Приложение работает под отдельным пользователем `yt-app`, политика разрешает доступ только к бакетам
  `yt-raw` и `yt-media`. root-учётка хранилища используется только в `storage-init`.

## Запасной вариант

`bitnamilegacy/minio:2025.4.22` (+ `bitnamilegacy/minio-client`) — оригинальный MinIO, но образ
заморожен: обновлений безопасности не будет, Bitnami перевёл его в legacy-namespace.
Замена: другой `image` в compose и путь к `mc` в init-скрипте. Код приложения не меняется.

## Отвергнутые варианты

- **Сборка MinIO из исходников** в Dockerfile: деплой на ВМ дольше на 3–5 минут, сборка зависит
  от GitHub и Go proxy.
- **RustFS**: молодой проект, есть риск несовместимости в multipart/presigned.
- **SeaweedFS / Garage**: другая модель администрирования (identities через конфиг), опыт
  работы с MinIO и `mc` не переносится.

## Последствия

- Зависимость от стороннего форка: следим за релизами `pgsty/silo`, обновляем тег осознанно.
- Образ silo запускается от root внутри контейнера (так устроен upstream-образ). Наружу хранилище
  не опубликовано; риск принят (docs/security.md).
