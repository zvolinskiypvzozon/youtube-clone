# ADR 0003: Фоновая обработка — очередь в Postgres, транскод в MP4 360p/720p

- Статус: принято
- Дата: 2026-11-07

## Контекст

После загрузки видео нужно проверить файл, узнать длительность, сделать превью и версии
для воспроизведения в браузере. Это долгие операции, выполнять их в HTTP-запросе нельзя.

## Решение

**Очередь.** Таблица `jobs` в Postgres. Worker забирает задачу запросом
`SELECT … FOR UPDATE SKIP LOCKED LIMIT 1`, держит lease (`locked_until`), делает повторы
с ограничением числа попыток и записывает последнюю ошибку.

- Задача создаётся **в той же транзакции**, что и перевод видео в `processing`. Поэтому
  не бывает ни видео без задачи, ни задачи без видео (transactional outbox бесплатно).
- Компонентов меньше: без Redis/RabbitMQ.

**Формат.** ffprobe проверяет, что файл — реальный медиаконтейнер с видеопотоком
длиной не больше 60 минут. ffmpeg делает MP4 H.264/AAC 360p и 720p (не выше исходного
разрешения) с `-movflags +faststart` и кадр-превью JPEG. Плеер выбирает качество.

### Уточнения при реализации (день 3)

**Очередь** (контракт — docstring `app/models/job.py`, SQL — `app/repositories/jobs.py`):
- захват `SKIP LOCKED`, lease 15 минут, heartbeat продлевает его раз в минуту;
- **fencing-токен** `locked_by` (новый на каждый захват). Завершить, провалить или вернуть задачу
  можно только со своим токеном. Worker, чей lease истёк и чью задачу перехватили, не перезапишет
  чужой результат;
- **ключи результатов содержат токен попытки** (`videos/{id}/{token}/360p.mp4`). Иначе, убирая
  «свои» объекты, такой worker удалил бы файлы того, кто перехватил задачу;
- исходы обработки: `ready`; `failed` (файл непригоден — без повторов); `retry` (временный сбой —
  пауза 30·2ⁿ⁻¹ с, до 3 попыток); `lost` (задачу перехватили или видео удалено — результат
  отбрасывается, свои объекты удаляются);
- финализация одной транзакцией: задача `done` (с токеном), строки `video_files`, статус `ready`,
  `published_at` (если не приватное). Исходник удаляется после commit (решение архитектора:
  диск ВМ ограничен), в том числе для непригодных файлов. Если commit мог выполниться, но ответ
  потерян, объекты не удаляются (иначе `ready` с 404); сироты убирает maintenance;
- SIGTERM (деплой): задача сразу возвращается в очередь, попытка не засчитывается.

**Периодические задачи** (раз в 5 минут): возврат задач упавших worker-ов (по лимиту попыток —
в очередь или `failed`), удаление истёкших сессий и брошенных загрузок (старше 24 часов),
удаление объектов `yt-media` без ссылок из БД (старше 2 часов).

**Лимит «в работе»:** не больше 3 видео в статусах `uploading` + `processing` на пользователя —
иначе один пользователь занял бы очередь единственного worker-а.

**Безопасность ffmpeg** — `docs/security.md`, раздел «Обработка видео».

## Альтернативы

- **Redis + arq/Celery**: стандартно, но добавляет сервис и теряет атомарность с БД.
- **HLS (адаптивный стриминг)**: ближе к оригинальному YouTube, но сегментов сотни, и для приватных
  видео пришлось бы подписывать каждый или ставить auth-прокси. Отложено, можно добавить позже.

## Последствия

- Postgres-очередь рассчитана на десятки задач в минуту. Для такой нагрузки этого достаточно,
  а при росте можно заменить её на брокер за тем же интерфейсом.
- Транскод нагружает CPU. Сейчас работает один worker с одной задачей за раз; ffmpeg запускается
  с ограничением потоков. Жёсткие лимиты CPU в compose не заданы: на ВМ с 1 vCPU `cpus: 2` не дал бы
  стеку стартовать.
