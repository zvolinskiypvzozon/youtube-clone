# ADR 0003: Фоновая обработка — очередь в Postgres, транскод в MP4 360p/720p

- Статус: принято
- Дата: 2026-11-07

## Контекст

После загрузки видео нужно проверить файл, узнать длительность, сделать превью и версии
для воспроизведения в браузере. Это долгие операции, выполнять их в HTTP-запросе нельзя.

## Решение

**Очередь.** Таблица `jobs` в Postgres. Worker забирает задачу запросом
`SELECT … FOR UPDATE SKIP LOCKED LIMIT 1`, держит lease (`locked_until`), делает повторы
с ограничением числа попыток и записывает последнюю ошибку.

- Задача создаётся **в той же транзакции**, что и перевод видео в `processing`. Поэтому
  не бывает ни видео без задачи, ни задачи без видео (transactional outbox бесплатно).
- Компонентов меньше: без Redis/RabbitMQ.

**Формат.** ffprobe проверяет, что файл — реальный медиаконтейнер с видеопотоком
длиной не больше 60 минут. ffmpeg делает MP4 H.264/AAC 360p и 720p (не выше исходного
разрешения) с `-movflags +faststart` и кадр-превью JPEG. Плеер выбирает качество.

## Альтернативы

- **Redis + arq/Celery**: стандартно, но добавляет сервис и теряет атомарность с БД.
- **HLS (адаптивный стриминг)**: ближе к оригинальному YouTube, но сегментов сотни, и для приватных
  видео пришлось бы подписывать каждый или ставить auth-прокси. Отложено, можно добавить позже.

## Последствия

- Postgres-очередь рассчитана на десятки задач в минуту. Для такой нагрузки этого достаточно,
  а при росте можно заменить её на брокер за тем же интерфейсом.
- Транскод нагружает CPU. Сейчас работает один worker с одной задачей за раз; ffmpeg запускается
  с ограничением потоков. Жёсткие лимиты CPU в compose не заданы: на ВМ с 1 vCPU `cpus: 2` не дал бы
  стеку стартовать.
