# ADR 0006: Модель видимости видео и единая политика доступа

- Статус: принято
- Дата: 2026-11-07

## Решение

Видимость определяют три независимых признака видео:

| Признак | Значения | Кто меняет |
|---|---|---|
| `visibility` | `public`, `unlisted`, `private` | владелец |
| `status` | `uploading`, `processing`, `ready`, `failed` | система |
| `moderation` | `ok`, `hidden` | модератор/админ |

Кто видит видео:

| Зритель | public | unlisted | private | hidden модерацией |
|---|---|---|---|---|
| Аноним / чужой | лента, поиск, канал, ссылка | только по ссылке | нет (404) | нет (404) |
| Из списка допуска (`video_access`) | да | да | по ссылке и в «Доступные мне» | нет |
| Владелец | да | да | да | да, с пометкой «Скрыто модератором» |
| Модератор / админ | да | да | да | да |

- Видео со статусом не `ready` видят только владелец и модераторы/админы.
- Вся логика собрана в одном модуле `app/services/policies.py`:
  - `can_view(viewer, video) -> bool` для единичных запросов;
  - `visible_videos_filter(viewer)` — SQL-условие для лент, поиска, канала и плейлистов.
  - *Изменено, см. Дополнение 1: три правила вместо одного SQL-условия.*
- Чужим отвечаем 404, а не 403: так не раскрывается факт существования приватного видео.
- Комментарии, лайки и счётчики доступны только тем, кто может видеть видео.

## Последствия

- Новый путь выдачи видео без политики — дефект, ловится ревью (агент `reviewer`)
  и матричными тестами.

## Дополнение 1 (2026-11-07, день 4): каталог и «видимое мне» — разные правила

Таблица выше задаёт два разных вопроса: «можно ли открыть это видео» и «показывать ли его
в каталоге». Unlisted и приватное с допуском открыть можно, но в ленту, поиск и на страницу
канала они не попадают. Плейлисты, «Доступные мне», история и понравившиеся при этом
показывают всё, что зритель может открыть. Поэтому вместо одного `visible_videos_filter`
в `app/services/policies.py` три правила:

| Правило | Где применяется | Что пропускает |
|---|---|---|
| `can_view(viewer, facts)` | карточка по ссылке, URL потока, комментарии, реакции | таблица выше |
| `visible_filter(viewer)` | плейлисты, «Доступные мне», история, понравившиеся | SQL-аналог `can_view` |
| `listed_filter()` | лента, поиск, страница канала | `ready ∧ public ∧ ok` для любого зрителя, включая владельца и модераторов |

Плюс `can_manage(viewer, owner_id)`: правка, список допуска, удаление — только владелец;
его SQL-аналог `owned_filter(viewer)` — «Мои видео» (день 4).
Права модерации (день 6) — отдельная функция, не расширение `can_manage`.

- Свои видео в любом статусе владелец видит в «Моих видео», модераторы — в модерации,
  а не в каталоге.
- Константы в `listed_filter` — SQL-литералы, а не bind-параметры: так условие совпадает
  с предикатом частичного индекса `ix_videos_feed`, и generic-план prepared statement его
  использует.
- `tests/test_policies.py`: матрица 6 зрителей × 24 состояния видео (visibility × status ×
  moderation) на двух каналах; `can_view`, `can_view` на фактах из БД и `visible_filter`
  обязаны дать ровно ожидаемые множества.

## Дополнение 2 (2026-11-08, день 4): отказ в управлении — 404 или 403

Правило «чужим отвечаем 404» защищает факт существования видео, которое зритель не может
открыть. Для операций управления (правка, список допуска, удаление) зритель бывает двух видов:

| Зритель | Ответ |
|---|---|
| Не может открыть видео (`can_view` = false) | 404, тот же, что для несуществующего |
| Может открыть, но не владелец (`can_manage` = false): чужое public/unlisted, допущенный к private, модератор, админ | 403 |
| Аноним | 401 |

Существование видео, которое зритель может открыть, ему и так известно, поэтому 404 был бы
неправдой и только путал бы клиента. Права модераторов (день 6) — отдельная функция; через
эндпоинты владельца они получают 403.

Порядок в сервисе: сначала права (чтение без блокировки), потом блокировка строки
`FOR NO KEY UPDATE` — чужие запросы не ставят строку видео в очередь блокировок.

## Дополнение 3 (2026-11-09, день 4): удаление видео и занятость строки

Удаление (`DELETE /api/videos/{id}`) — те же права и ответы, что у правки. Сервис удаления
(`services/deletion.py`) от роли не зависит: права проверяет вызывающий (владелец сегодня,
модерация — день 6).

**Порядок блокировок «задачи → видео».** Worker (`_finalize`, `_fail_permanently`) сначала
обновляет строку задачи, потом блокирует видео; каскадный `DELETE videos` тоже блокирует
задачи. Удаление в обратном порядке взаимно блокировалось бы с финализацией. Поэтому:
`jobs … FOR UPDATE` → `videos … FOR UPDATE` → повторное чтение набора задач. Если
параллельный `complete_upload` (держал видео) добавил задачу, — rollback и повтор, не более
3 раз, затем 503. **Любой новый путь, удаляющий видео** (бан или удаление пользователя
и канала на дне 6 — каскад users → channels → videos → jobs идёт в обратном порядке),
обязан идти через `services/deletion` или брать задачи первыми.

**Хранилище — после commit.** Ключи собираются под блокировкой, объекты (multipart и
исходник в `yt-raw`, префикс `videos/{id}/` в `yt-media`) удаляются после commit. Сбой
хранилища не роняет ответ: остатки убирает maintenance (сироты `yt-media` по ссылкам,
сироты `yt-raw` — по отсутствию строки видео, оба с порогом `ORPHAN_MEDIA_MINUTES`).
Исходники `ready`/`failed`-видео, которые worker не смог удалить, уборка тоже снимает;
видео в `uploading`/`processing` она не трогает при любом возрасте — долгая загрузка не
обрывается.

**`lock_timeout`.** API ждёт чужую блокировку строки не дольше 5 с (`DB_LOCK_TIMEOUT_MS`),
worker — 30 с. Таймаут действует на все блокировки соединения API (строки, advisory-лок
смены ролей), поэтому общий текст 503 нейтральный, а удаление задаёт свой. Истёкший таймаут (`55P03`) и взаимная блокировка (`40P01`) в API — **503
с `Retry-After: 2`**: это временная занятость, а не конфликт состояния ресурса (409).
У worker-а таймаут — обычный временный сбой: задача уходит в повтор.

## Дополнение 4 (2026-11-09, день 5): взаимодействие только с не скрытым видео

Реакции и новые комментарии — публичное взаимодействие: разрешены только к готовому и не
скрытому модератором видео (`policies.can_interact`), для любого зрителя, включая владельца,
модераторов и админов. Видеть скрытое видео staff может (разбор), голосовать и писать — нет.
Порядок: `can_view` (иначе 404), затем `can_interact` (иначе 409 с причиной — тем, кто видео
видит, существование и так известно). Чтение комментариев — по `can_view`.

**Просмотры** (`POST /api/videos/{id}/view`) — особый случай: доступ `can_view` (404), не готово
— 409, но скрытое модератором видео отвечает **204 без засчитывания**, а не 409: плеер владельца
или модератора не должен получать ошибку, а их просмотр скрытого — разбор, не просмотр.
Счётчик меняется атомарным `UPDATE` с условиями политики (`visible_filter(viewer)` и
`interactable_filter()`, SQL-аналог `can_interact`) прямо в запросе: если `UPDATE` ждал
блокировку (PATCH делал видео приватным), условие проверяется заново по новой версии строки.
Остаётся окно для отзыва допуска (он строку видео не блокирует): последствие — +1 просмотр,
данные не раскрываются.

## Дополнение 5 (2026-11-10, день 5): комментарии — кто читает, пишет и удаляет

- **Читать** (`GET /api/videos/{id}/comments`) — `can_view` (иначе 404), в том числе под
  скрытым видео: владелец и staff разбирают его вместе с комментариями.
- **Писать** (`POST`) — `can_view` (404), затем `can_interact` (409, доп. 4). Условия политики
  (`visible_filter(viewer)` + `interactable_filter()`) стоят в самом `UPDATE comments_count`,
  который выполняется до `INSERT` и держит строку видео до commit: видео, ставшее приватным или
  скрытым, пока запрос ждал блокировку, комментарий не получит (тесты). Окно отзыва допуска —
  как у просмотров (отзыв строку видео не блокирует): последствие — один комментарий от
  пользователя, только что потерявшего допуск; владелец может его удалить.
- **Удалять** (`DELETE /api/comments/{id}`) — `policies.can_delete_comment`: автор или
  владелец видео (любой комментарий под своим видео). Решения архитектора 2026-11-10:
  - staff удаляет комментарии через модерацию **дня 6**, не через этот эндпоинт (как и
    `can_manage` для видео, роль прав не даёт);
  - удаление разрешено и под скрытым видео: убрать контент — не взаимодействие;
  - автор удаляет свой комментарий и после потери допуска к приватному видео — это его данные;
  - комментарий не виден (нет `can_view` на видео, или нет такого) — 404 с одним текстом;
    виден, но прав нет — 403: сам комментарий зритель и так видит в списке.
- **Порядок блокировок «задачи → видео → комментарии»** (дополнение к доп. 3). Удаление
  комментария сначала блокирует строку видео, затем `DELETE … RETURNING`, и уменьшает счётчик,
  только если строку удалил этот запрос (два параллельных удаления — один раз −1). В обратном
  порядке оно взаимно блокировалось бы с удалением видео: то держит видео и каскадом ждёт строки
  комментариев.
- **Вывод — только как текст.** Сервер хранит и отдаёт текст как есть, без экранирования и
  очистки HTML; фронтенд (день 7) выводит его текстовым узлом, без `dangerouslySetInnerHTML`.

## Дополнение 6 (2026-11-10, день 6): жалобы и модерация

- **Жалоба** (`POST /api/videos/{id}/reports`, категория + необязательное пояснение до 500
  символов): `can_view` (404, неотличимо от несуществующего) → своё видео — 400 →
  `can_interact` (не готово или уже скрыто — 409, в том числе для staff) → одна открытая
  жалоба пользователя на видео (409). Дубль сначала отсекает быстрая проверка без блокировки
  (поток повторов не держит строку видео — аудит шага 4, Medium), окончательно —
  `ON CONFLICT` по частичному уникальному индексу `uq_reports_open_video_reporter`. После
  закрытия жалобы можно пожаловаться снова.
- **Жалобы видит только staff** (`GET /api/admin/reports`, moderator и admin). Владелец видео
  не узнаёт, кто пожаловался: в его ответах только `moderation_reason` — причина скрытия
  (тесты: карточка и «Мои видео» владельца не содержат пожаловавшихся; очередь для владельца
  и любого user — 403). Ответ на жалобу пожаловавшегося тоже не содержит.
- **Снимок.** Жалоба хранит название видео и handle канала на момент жалобы (под
  блокировкой строки видео). Удаление видео обнуляет `reports.video_id` (`SET NULL`), снимок
  и статус остаются — история модерации не пропадает. Владелец может удалить скрытое видео
  (решение 2026-11-09).
- **Скрытие и возврат** (`PUT /api/admin/videos/{id}/moderation`, staff): скрытие требует
  причину (её видит владелец), закрывает открытые жалобы видео как `resolved`; возврат
  снимает причину, закрытые жалобы **не открываются** (решение архитектора 2026-11-10) —
  история в журнале. Повтор того же состояния — без изменений и без записи в журнал.
- **Отклонение жалобы** (`POST /api/admin/reports/{id}/dismiss`, staff): только открытой
  (закрытая — 409), видео не меняется.
- **Своё видео (решение архитектора 2026-11-10):** модератор не скрывает и не возвращает своё
  видео, не отклоняет жалобы на него (403) и не видит их в очереди — иначе узнал бы автора
  жалобы и судил бы сам себя (`policies.can_moderate`, `moderation_queue_filter`; для
  удалённого видео «своё» — по снимку handle, handle неизменяем). Админу можно, действие
  пишется в журнал с пометкой `own_video`. Права проверяются до блокировки строки видео.
  Предпосылка «handle неизменяем»: если появится смена handle или удаление канала, жалобе
  нужен снимок `channel_id` (без внешнего ключа) вместо сравнения по handle.
- **Удаление комментария staff** — тем же `DELETE /api/comments/{id}`: `can_delete_comment`
  разрешает staff (меняет доп. 5, где staff откладывался до модерации). Удаление staff
  (не автором и не владельцем видео) пишется в журнал со снимком текста.
- **Журнал** `moderation_log`: кто, что, над чем, причина, снимок цели (`details`). Цель — без
  внешнего ключа: запись переживает удаление видео, комментария, пользователя.
- **Порядок блокировок «видео → жалобы»** (дополнение к доп. 3 и 5; полный порядок —
  «задачи → видео → комментарии / жалобы»):
  - жалоба: строка видео `FOR SHARE` с условиями политики в самом запросе, затем `INSERT`;
  - скрытие: строка видео `FOR NO KEY UPDATE` (`lock_for_edit`), затем `UPDATE` открытых
    жалоб. `FOR SHARE` и `FOR NO KEY UPDATE` конфликтуют, поэтому жалоба, держащая строку,
    будет закрыта скрытием после своего commit (тест «скрытие ждёт жалобу и закрывает её»;
    защита продублирована: без явной блокировки скрытие ждёт жалобу на неявной блокировке
    `UPDATE videos` при autoflush, поэтому мутация ловится только вместе с переносом
    закрытия жалоб до изменения строки видео),
    а жалоба, пришедшая во время скрытия, ждёт его и получает 404/409 (тест);
  - отклонение: жалоба читается без блокировки (ради `video_id`), затем строка видео, затем
    `UPDATE` жалобы. Обратный порядок взаимно блокировался бы с удалением видео: оно держит
    строку видео `FOR UPDATE` и каскадом (`SET NULL`) ждёт строки жалоб. Тест «отклонение ждёт
    удаление видео» проверяет, что отклонение дожидается удаления и отклоняет жалобу с
    `video_id = NULL`; саму взаимоблокировку при обратном порядке (нужно точное чередование
    двух транзакций) тест не воспроизводит — порядок закреплён кодом и ревью;
  - удаление видео: задачи → видео → жалобы (каскад `SET NULL`), `services/deletion`.
- **Принятые риски:** отзыв допуска к приватному видео, пока жалоба ждёт блокировку, не
  учитывается (`video_access` читается по снимку начала запроса — как у комментариев
  и просмотров; жалобу видит только staff, пользователю ничего не раскрывается). Поток жалоб
  с многих аккаунтов может удерживать `FOR SHARE` на строке видео и задерживать скрытие
  и правку (до `lock_timeout` 5 с → 503) — до rate limit шага 2 дня 6.

## Дополнение 7 (2026-11-10, день 6): плейлисты

Решения архитектора 2026-11-09 и 2026-11-10: плейлисты минимальные (создать, изменить,
удалить, добавить и убрать **своё** видео, список на канале); чужие видео в плейлист не
добавляются и в перенос не вносятся.

| Правило (`app/services/policies.py`) | Где | Что пропускает |
|---|---|---|
| `can_view_playlist(viewer, owner_id, visibility)` | карточка и состав плейлиста | `public`, `unlisted` — всем, включая анонима; `private` — **только владельцу** |
| `listed_playlists_filter()` | страница канала | только `public`, одинаково для любого зрителя, включая владельца и staff |
| `visible_filter(viewer)` | состав, `video_count`, превью | видео, которые может открыть **текущий** зритель (доп. 1) |
| `can_manage(viewer, owner_id)` | правка, удаление, добавление и удаление видео | только владелец |

- **Staff приватный плейлист не видит** (404, как посторонний): модерации плейлистов нет,
  разбирать там нечего. Это отличие от видео, где staff видит приватные для разбора.
  Видимость плейлиста в ответах — только владельцу.
- **Состав фильтруется по текущему зрителю**, а не по владельцу плейлиста: иначе зритель
  увидел бы приватные видео, допущенные владельцу. Недоступное видео не показывается совсем
  (без заглушки «видео недоступно») и не учитывается в `video_count` и превью — иначе они
  раскрывали бы существование приватных и скрытых видео. Владелец видит свои видео в любом
  состоянии со `state`; staff — состав открытого ему плейлиста целиком (по `visible_filter`).
- **Отказ в управлении** — как доп. 2: аноним 401, не может открыть плейлист — 404, может,
  но не владелец — 403. Добавить чужое видео: зритель его видит — 403, не видит — 404.
- **Счётчика видео в плейлисте нет**: число считается запросом по видимым зрителю видео —
  при бане (шаг 3) и удалении пользователя (день 9) пересчитывать нечего. Правило «канал
  забаненного — 404» (шаг 3) распространится и на плейлисты: `can_view_playlist` уже
  принимает владельца.
- **Лимиты:** 200 плейлистов на канал, 5000 видео в плейлисте.
- **Порядок блокировок** (дополнение к доп. 3, 5, 6):
  - создание: строка канала `FOR NO KEY UPDATE` → подсчёт → `INSERT` (иначе два создания на
    границе лимита оба увидели бы 199). С `FOR KEY SHARE` внешних ключей совместима;
  - добавление «**плейлист → видео**»: права без блокировок → строка плейлиста
    `FOR NO KEY UPDATE` (позиция `max + 1` и лимит) → строка видео `FOR KEY SHARE` с условием
    «видео этого канала» в самом запросе → `INSERT … ON CONFLICT DO NOTHING`. Явная блокировка
    видео нужна, чтобы добавление, дождавшееся удаления видео, получило 404, а не нарушение
    внешнего ключа (500). Вторая защита позиции — `UNIQUE (playlist_id, position)`;
  - удаление элемента: строка плейлиста → `DELETE` элемента;
  - удаление видео остаётся «задачи → видео → комментарии / жалобы / элементы плейлистов»
    (каскад). Строки `playlists` оно не блокирует (удаление ссылающейся строки родителя не
    трогает), значит ни один путь не берёт видео раньше плейлиста — цикла нет;
  - удаление плейлиста (`DELETE`, каскад элементов) ждёт идущее добавление; добавление
    после удаления — 404;
  - удаление пользователя (день 9) — каскад «канал → плейлисты → элементы» вместе с видео
    через `services/deletion`.
- **Взаимоблокировка с пакетной очисткой брошенных загрузок** (аудит шага 6, Low): в плейлисте
  могут лежать свои видео в статусе `uploading`. Каскад `DELETE playlists` и каскад пакетного
  `delete_stale_uploads` (maintenance) берут строки `playlist_items` в разном порядке, и при
  двух таких элементах возможен `40P01`. Последствие — 503 с `Retry-After` у удаления плейлиста
  или откат одного прохода очистки (она повторится). Данные целы, поэтому риск принят.
- Тесты гонок: удаление видео ждёт добавление и каскадом убирает новый элемент; добавление
  ждёт удаление видео — 404; два добавления — разные позиции; добавления и создания на границе
  лимита — 409; добавление ждёт удаление плейлиста — 404.
