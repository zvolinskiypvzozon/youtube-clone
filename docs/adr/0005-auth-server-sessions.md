# ADR 0005: Аутентификация — серверные сессии в HttpOnly cookie

- Статус: принято (уточнено по итогам ревью и аудита на дне 2)
- Дата: 2026-11-07

## Решение

**Сессии**
- При входе и регистрации сервер создаёт случайный токен (256 бит). В таблице `sessions`
  хранится только SHA-256 токена, срок жизни (30 дней) и метаданные (IP, User-Agent ≤ 300 символов).
- Cookie `session`: `HttpOnly`, `SameSite=Lax`, `Path=/`. `Secure` включается через
  `COOKIE_SECURE=true` при HTTPS (по ТЗ проверка идёт по HTTP на IP).
- Каждый вход выдаёт новый токен (фиксация сессии невозможна). Если браузер уже присылает
  cookie-сессию, она удаляется в той же транзакции: при повторном входе старые сессии
  не остаются «сиротами».
- Выход удаляет сессию в БД и очищает cookie. Он идемпотентен: без действующей сессии
  ответ тоже 204, cookie очищаются.
- **Бан проверяется на каждом запросе** (`users.is_banned` в `authenticate`). Он действует
  мгновенно на все сессии, даже если их не удалять.

**Пароли**
- argon2id (argon2-cffi, профиль RFC 9106: 64 МиБ, t=3, p=4), длина 8–128.
- Хэширование выполняется в отдельном потоке. В процессе одновременно идут не больше двух
  вычислений (семафор): поток входов не исчерпает память.
- Вход не раскрывает, существует ли пользователь: одинаковый 401 и выравнивание времени
  проверкой фиктивного хэша. О бане сообщается (403) только после верного пароля.

**CSRF — два слоя**
1. Middleware отклоняет `POST/PUT/PATCH/DELETE`, если `Origin` (схема + хост + порт) не совпадает
   с адресом запроса. Это закрывает и login CSRF, где сессии ещё нет. Запросы без `Origin` (не браузер)
   пропускаются.
2. Для запросов с cookie-сессией — заголовок `X-CSRF-Token`, равный `HMAC(SECRET_KEY, токен сессии)`.
   То же значение сервер кладёт в читаемую JS cookie `csrf`, но проверяет по вычисленному
   значению, а не по cookie. Подложенная cookie (например, с другого порта того же IP)
   не поможет.

**Swagger и API-клиенты**
- `POST /api/auth/token` (OAuth2 password flow) выдаёт Bearer-токен. Это та же сессия в таблице
  `sessions`. Для Bearer CSRF не нужен: браузер его сам не подставляет.
- Браузерный `/api/auth/login` токен в теле не возвращает, только как HttpOnly-cookie.

**Прочее**
- Ответы `/api/auth/*` идут с `Cache-Control: no-store`.
- Rate limit nginx: 10/мин с IP (burst 10) только на `login`, `register`, `token`.

## Альтернативы

- **JWT access + refresh**: stateless, но мгновенный отзыв (бан, выход) всё равно требует
  хранилища, а хранение токена в JS открывает его для XSS.

## Последствия

- Каждый аутентифицированный запрос — один запрос к БД по уникальному индексу (`token_hash` + JOIN
  `users`). `last_seen_at` обновляется не чаще раза в 10 минут.
- Истёкшие сессии нужно периодически удалять (индекс `ix_sessions_expires_at` есть); задача
  появится в периодических заданиях worker (день 3).
- Регистрация сообщает, что email или имя заняты: это принятый риск, см. `docs/security.md`.
