# ADR 0004: Загрузка и раздача через presigned URL, хранилище за nginx на том же origin

- Статус: принято
- Дата: 2026-11-07

## Контекст

Видео весит до 2 ГБ. Если гнать байты через API, uvicorn-воркеры будут заняты, потребуются
буферы и таймауты. Плеер должен поддерживать перемотку (Range), а приватные видео нельзя
отдавать без проверки прав.

## Решение

- **Загрузка**: S3 multipart upload. API создаёт upload и выдаёт presigned PUT на каждую часть,
  браузер грузит части сам (прогресс через XHR), затем вызывает `complete`. Ключи объектов
  генерирует сервер (`raw/{video_id}/source`), клиент не выбирает путь.
- **Раздача**: API проверяет политику доступа и выдаёт presigned GET с коротким TTL.
  Range и перемотку обеспечивает само хранилище.
- **Тот же origin**: nginx проксирует `/yt-raw/*` и `/yt-media/*` в хранилище **с сохранением
  заголовка `Host`**. Подпись SigV4 включает host, поэтому API подписывает URL на тот host, с которого
  пришёл запрос браузера. В результате:
  - не нужен CORS, хранилище не публикуется отдельным портом;
  - нет настройки `PUBLIC_HOST`: работает по любому IP (сетевой мост VirtualBox, DHCP).
  - *Изменено, см. Дополнение 1: подпись на постоянный внутренний host, ссылки относительные.*
- Бакеты закрыты: без подписи → 403. Проверено (ADR 0002).

### Уточнения при реализации загрузки (день 3)

- **Длина каждой части входит в подпись** (`Content-Length` в SignedHeaders): части по 16 МиБ,
  последняя — остаток, сумма равна заявленному размеру. Хранилище отклоняет часть любой другой
  длины (проверено на silo: ±1 байт → 403 `SignatureDoesNotMatch`). Без этого presigned UploadPart
  не ограничивал длину, и «заявить 2 ГБ» означало бы до 16 ГиБ (128 частей × 128 МиБ лимита nginx).
  В nginx для `/yt-raw/` `client_max_body_size 17m`.
- **TTL ссылок на загрузку — 1 час** (раздача — короткий). Загрузка 2 ГБ на медленном канале идёт
  десятки минут, перевыпуска ссылок пока нет. Подписи не пишутся в access log nginx
  (формат без query-строки).
- Хост для подписи проверяется (`host[:port]`, IPv6 в скобках). Некорректный Host → 400 до создания
  загрузки. Кэш клиентов для подписи ограничен (32), потому что ключ кэша приходит из запроса.
  *Заменено Дополнением 1.*
- **Лимит видео «в работе»** (3 на пользователя: загрузка + обработка) сериализован блокировкой
  строки канала.
- `complete` идемпотентен к сбою «части склеены, commit не прошёл». `cancel` удаляет и незавершённую
  загрузку, и уже склеенный объект. Брошенные multipart хранилище удаляет само через 24 часа
  (`stale_uploads_expiry`); видео в `uploading` чистит периодическая задача worker.

## Альтернативы

- **Стриминг через API** (`StreamingResponse` + Range): проще контролировать доступ, но API
  становится узким местом.
- **nginx `auth_request` + `X-Accel-Redirect`**: проверка прав на каждый запрос без пересылаемых ссылок,
  но сложнее и требует проксирования с внутренней подписью.

## Последствия / принятый риск

- Presigned URL можно переслать, и до истечения TTL он работает у любого. TTL короткий,
  ссылка выдаётся только после проверки прав. Риск принят (docs/security.md).
- Имена бакетов зашиты в location nginx. Это осознанно: короткий явный список.
- Host приходит из запроса клиента, поэтому подпись выдаётся только для того host, с которого
  клиент обратился. Подменить ссылку для другого пользователя таким способом нельзя.
  *Изменено, см. Дополнение 1.*

## Дополнение 1 (2026-11-07, день 4): подпись на постоянный host, относительные ссылки

**Проблема** (аудит шага 2 дня 4, High). Подпись на Host запроса требовала клиента boto3
на каждый новый Host. Создание клиента стоит ~0,35 с CPU и идёт под общей блокировкой
(замер в контейнере api: 10 клиентов — 3,5 с CPU). С появлением анонимной ленты, где
подписываются превью, любой мог перебором `Host` (nginx пропускает 20 запросов/с с IP)
занять оба процесса API и вытеснить из кэша клиента настоящего Host.

**Решение.**
- API подписывает все ссылки одним клиентом на постоянный внутренний host
  `media.internal` (константа `SIGNING_HOST` в `app/core/storage.py`) и отдаёт клиенту **относительный** URL:
  `/yt-media/<key>?X-Amz-…`. Браузер сам подставляет origin, с которого открыт сайт.
- nginx в `/yt-raw/` и `/yt-media/` передаёт хранилищу `Host: media.internal`
  (`infra/nginx/storage-proxy.conf`), и подпись сходится. Host клиента в подпись не входит.
- `S3_PUBLIC_ENDPOINT` остаётся для автотестов (клиент ходит в хранилище напрямую,
  ссылки абсолютные).

**Что сохраняется:** тот же origin без CORS, работа по любому IP или имени без настройки
`PUBLIC_HOST`, бакеты закрыты.

**Следствия.**
- Проверка формата Host и кэш клиентов по Host больше не нужны (удалены).
- Снаружи ссылку можно открыть только через наш nginx: хранилище не опубликовано, а с другим
  Host подпись не сойдётся (тест `test_relative_url_valid_only_via_signing_host`).
- Тест `test_signing_does_not_depend_on_request_host`: 40 запросов с разными Host — один клиент
  подписи. На стеке: 40 запросов ленты с разными Host за 1,0 с.
- `SIGNING_HOST` и `proxy_set_header Host` в nginx обязаны совпадать (константа, не настройка
  из env). Расхождение ломает загрузку и просмотр сразу, его ловит smoke-тест.
- nginx сбрасывает `X-Forwarded-Host` и `Forwarded` от клиента. `MINIO_DOMAIN` в хранилище
  не задаётся: иначе `media.internal` при `MINIO_DOMAIN=internal` стал бы бакетом `media`.
- Ответы `/yt-media/` идут с `Cache-Control: private, max-age=900` (без `always` — ошибки
  не кэшируются): общие кэши байты не хранят, браузер — до 15 минут **с момента получения**.
  После отзыва доступа байты могут оставаться в кэше этого браузера до ~2×TTL от подписи.
- API-клиенты (Bearer) получают относительные URL и подставляют origin, с которого вызывали API.
  SPA и медиа — один origin (CSP `'self'`); CDN или отдельный медиадомен потребуют нового ADR.
