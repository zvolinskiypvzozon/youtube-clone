# Проверка деплоя на чистой Ubuntu 24.04

Цель: убедиться, что `sudo ./deploy.sh` на системе «из коробки» поднимает весь стек (K1),
и повторить это сколько угодно раз с одного и того же чистого состояния.

Основной способ — отдельный дистрибутив WSL `yt-clean`, который сбрасывается из tar-снимка.
Запасной вариант — ВМ VirtualBox со снимком (раздел в конце).

## Способ 1: WSL-дистрибутив `yt-clean`

### Подготовка (один раз, PowerShell на Windows)

Снимок и файлы дистрибутива лежат в `$HOME\wsl\` профиля Windows
(у автора — `C:\Users\Федор\wsl\`). Каталог создаётся один раз: `mkdir $HOME\wsl`.

```powershell
# Чистая Ubuntu 24.04 отдельным дистрибутивом
wsl --install -d Ubuntu-24.04 --name yt-clean
# Внутри: создать пользователя по запросу установщика, больше ничего не ставить.
# Проверить, что systemd включён (на свежих образах Ubuntu — по умолчанию):
#   cat /etc/wsl.conf   ->  [boot] systemd=true
# Зафиксировать DNS — см. раздел «DNS в WSL» ниже (обязательно до экспорта снимка).

wsl --terminate yt-clean
wsl --export yt-clean $HOME\wsl\yt-clean.tar      # эталонное «чистое» состояние
```

Снимок — это Ubuntu «из коробки» плюс одна настройка среды: статический DNS.
Она нужна только тестовой среде WSL, на обычном сервере она не требуется. Сам проект
в снимке ничего не настраивает.

### Сброс к чистому состоянию (перед каждой проверкой)

```powershell
wsl --unregister yt-clean
wsl --import yt-clean $HOME\wsl\yt-clean $HOME\wsl\yt-clean.tar
```

После `--import` дистрибутив запускается под root, если в `/etc/wsl.conf` нет секции
`[user] default=<имя>`. Для проверки это не важно: `deploy.sh` всё равно работает от root.

### Перед запуском: общий сетевой стек WSL2

Все дистрибутивы WSL2 работают в одной служебной ВМ и **делят одно сетевое пространство имён**
(общие порты, интерфейсы, iptables). Отсюда два требования:

1. **Порт 80 свободен.** Его не должен занимать стек проекта или что-то другое в любом дистрибутиве.
   Проверка: `ss -ltn 'sport = :80'` — вывод должен быть пустым.
2. **Docker в других дистрибутивах остановлен.** Второй `dockerd` в `yt-clean` делил бы с первым
   мост `docker0` и правила iptables. Возможны сбои, не связанные с проектом. В рабочем дистрибутиве:
   ```bash
   docker compose down            # стек проекта (без -v — данные сохраняются)
   sudo systemctl stop docker docker.socket
   ```
   После проверки — **в таком порядке**:
   ```powershell
   wsl --terminate yt-clean          # остановить второй dockerd
   ```
   ```bash
   sudo systemctl restart docker     # именно restart, не start
   ```
   `dockerd` из `yt-clean` перестраивает общие правила iptables/nftables. После простого `start`
   контейнеры рабочего стека не видят друг друга (`dial tcp 172.x.x.x:9000: i/o timeout`
   в `storage-init`, `TimeoutError` в `migrate`), хотя мосты и подсети в порядке.
   `restart` заново создаёт правила Docker.

### DNS в WSL

**Симптом.** Первый прогон в `yt-clean` упал на скачивании:
`Could not resolve host: github.com`, `Could not resolve host: archive.ubuntu.com`.
Ошибка плавающая: часть запросов проходила, часть нет.

**Причина.** По умолчанию WSL сам генерирует `/etc/resolv.conf` (`generateResolvConf=true`) и
отправляет DNS-запросы через резолвер Windows. Этот путь бывает нестабилен: при смене сети,
VPN или после сна хоста. Проект тут ни при чём, но деплою нужен интернет: apt, Docker Hub,
PyPI, npm.

**Решение.** Отключить генерацию и прописать публичные DNS-серверы. Выполняется внутри
`yt-clean` **до** экспорта снимка, чтобы настройка была в эталонном состоянии:

```bash
# 1. Отключить автогенерацию resolv.conf (добавить секцию, остальные секции сохранить)
sudo tee -a /etc/wsl.conf >/dev/null <<'EOF'

[network]
generateResolvConf=false
EOF
```
```powershell
wsl --terminate yt-clean      # перезапуск, чтобы wsl.conf применился
wsl -d yt-clean
```
```bash
# 2. resolv.conf был симлинком на сгенерированный файл — заменить обычным файлом
sudo rm -f /etc/resolv.conf
printf 'nameserver 8.8.8.8\nnameserver 1.1.1.1\n' | sudo tee /etc/resolv.conf
getent hosts github.com archive.ubuntu.com registry-1.docker.io   # должны разрешаться
```
Затем `wsl --terminate yt-clean` и заново `wsl --export yt-clean $HOME\wsl\yt-clean.tar`.

**Защита в `deploy.sh`.** Перед любыми установками скрипт запускает `scripts/check-network.sh`.
Скрипт проверяет DNS (с тремя попытками) для всех нужных хостов: зеркала apt из источников системы,
`download.docker.com`, Docker Hub, `deb.debian.org`, PyPI, npm. Затем проверяет, что проходит HTTPS.
При проблеме деплой сразу останавливается с понятным сообщением и списком хостов, а не падает
через несколько минут на apt или `docker pull`. Пропустить проверку можно флагом
`--skip-network-check` (например, при локальном зеркале).

### Запуск

```powershell
wsl -d yt-clean
```
```bash
git clone https://github.com/zvolinskiypvzozon/youtube-clone
cd youtube-clone
time sudo ./deploy.sh
```

### Критерии успеха

- Скрипт завершился с кодом 0, сообщения «Готово» и адреса выведены.
  Первый запуск — несколько минут: установка Docker, скачивание образов, сборка.
- С Windows в браузере открываются `http://localhost/`, `http://localhost/docs`,
  `http://localhost/api/health` → `{"status":"ok","database":"ok","storage":"ok"}`.
  Адрес из вывода скрипта (`hostname -I`) — внутренний адрес WSL. С Windows используйте `localhost`.
- Повторный `sudo ./deploy.sh` проходит без ошибок, данные сохраняются.
- `sudo python3 scripts/smoke.py` проходит целиком: регистрация → загрузка видео (части напрямую
  в хранилище через nginx) → обработка worker-ом до `ready` → 360p, 720p, превью → хранилище без
  подписи 403. Тестовое видео генерирует ffmpeg из контейнера worker. Тот же скрипт запускает CI.

### Что прислать при ошибке

- последние ~30 строк вывода `deploy.sh` и время выполнения;
- `sudo docker compose ps -a`;
- `sudo docker compose logs --tail=100 <упавший сервис>`.

### Чем WSL отличается от настоящего сервера

| Аспект | WSL `yt-clean` | Ubuntu Server (ВМ, облако) |
|---|---|---|
| Ядро | общее ядро WSL (Microsoft) | собственное ядро Ubuntu |
| Сеть | общая с другими дистрибутивами, доступ с Windows по `localhost` | собственный IP |
| systemd | включается через `/etc/wsl.conf`; без него `deploy.sh` запускает Docker через `service` | есть всегда |
| unattended-upgrades сразу после загрузки | обычно не работает | работает; `deploy.sh` ждёт блокировку dpkg до 10 минут |
| DNS | генерируется WSL и бывает нестабилен — в снимке зафиксирован статически | обычный системный резолвер |

### Хэш вместо имени образа в `docker compose ps` (provenance)

На containerd image store (по умолчанию в Docker 29) BuildKit добавляет к образу
provenance-attestation с метаданными сборки. Из-за этого **каждая сборка даёт новый ID
образа**, даже если все слои из кэша. Тег переезжает на новый образ, а у контейнеров,
созданных на прежнем, `ps` показывает хэш. Проверено:

| | Две сборки подряд без изменений | `up --build` без изменений |
|---|---|---|
| attestation по умолчанию | ID меняется (`8c73…` → `5dcc…`) | api, web, worker пересоздаются каждый раз |
| ключи `build.provenance: false`, `build.sbom: false` в compose | **ID меняется** — compose 2.40 ключи принимает, но в сборку не передаёт | пересоздаются |
| `BUILDX_NO_DEFAULT_ATTESTATIONS=1` | ID одинаковый | ничего не пересоздаётся |
| то же + изменение кода | — | api и worker пересоздаются |

Риска «не пересоздать при изменении кода» нет: при изменении всегда новый ID. Проблема была
обратной: **лишнее пересоздание** контейнеров (рестарт) на каждом деплое без изменений.
Висячие образы на containerd store не копятся: старый образ удаляется сам, когда с него снят тег
и он не используется контейнером (проверено: `docker image rm` по старому ID → «No such image»).

Исправлено: `deploy.sh` выставляет `BUILDX_NO_DEFAULT_ATTESTATIONS=1`. Для ручного
`docker compose up --build` переменную нужно выставить самому (см. CLAUDE.md). Дополнительно
`deploy.sh` удаляет по ID прежние образы проекта, если тег с них снят: это нужно на классическом
хранилище overlay2 (установки, обновлённые со старых версий Docker), где они остаются висячими.
Чужие образы не затрагиваются. Фильтр по метке compose для этого не подходит: у висячих образов
меток нет.

Проверка в WSL покрывает основное: установку Docker, сборку, запуск, миграции, хранилище, nginx.
Сетевую часть настоящего сервера (доступ по IP из локальной сети) она не покрывает. Перед сдачей
желателен один прогон на ВМ (способ 2).

## Способ 2: ВМ VirtualBox (запасной, перед сдачей)

1. ВМ Ubuntu 24.04 Server, сеть «Сетевой мост», снимок `clean` сразу после установки.
2. Восстановить снимок `clean`, зайти по SSH, выполнить те же команды из раздела «Запуск».
3. Проверка с хоста: `http://<IP ВМ>/`, `/docs`, `/api/health`. IP выводит `deploy.sh`.
