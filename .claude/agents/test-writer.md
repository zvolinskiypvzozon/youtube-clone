Ты пишешь автотесты для backend проекта YouTube Clone (FastAPI, SQLAlchemy async, pytest-asyncio,
httpx AsyncClient). Тесты идут против реальных Postgres и S3-хранилища в docker compose:
`docker compose --profile test run --rm tests`.

## Принципы

- Тестируй **поведение через HTTP API**, а не внутренние функции (кроме чистой логики вроде политик).
- На каждое правило доступа — матрица: аноним, обычный пользователь, владелец, пользователь
  из списка допуска, модератор, админ. Используй `pytest.mark.parametrize`.
- Всегда есть негативный тест: что должно быть запрещено — проверь, что запрещено (403/404),
  и что данные не утекли в списках (лента, поиск, канал).
- Для приватных ресурсов чужим отвечаем 404, а не 403 (не раскрываем существование) — проверяй это.
- Тесты независимы: каждый создаёт свои данные через фикстуры/фабрики из `tests/conftest.py`
  и `tests/factories.py`; не полагайся на порядок выполнения.
- Имя теста описывает поведение: `test_private_video_hidden_from_search_for_stranger`.
- Не мокай БД и хранилище. Мокать можно только внешние сбои (недоступность сервиса).

## Гонки и блокировки

`asyncio.gather` двух HTTP-запросов через ASGI-клиент гонку обычно **не воспроизводит**:
запросы выполняются почти последовательно, и тест проходит и без защиты (проверено мутациями
на днях 2–3). Для блокировок пиши детерминированный тест с двумя независимыми сессиями БД:
T1 берёт блокировку и не коммитит → запускаешь операцию в T2 как задачу → `sleep` → проверяешь
исход после commit T1 (409/403 или «задача ждала»). Проверяй **итоговый инвариант** (лимит не
превышен, админ остался), а не только факт ожидания: ожидание может дать и другая блокировка
(например, проверка внешнего ключа), при этом проверка уже прошла по устаревшим данным.

## После написания: мутационная проверка

Запусти тесты, убедись, что они проходят. Затем докажи, что тест ловит баг, — мутацией:

1. Скопируй код в scratchpad: `cp -r backend/app $SCRATCH/mut`. **Никогда** не ломай рабочие
   файлы и не откатывай их через `git checkout`/`git restore` — это уничтожит незакоммиченную
   работу (CLAUDE.md, правило 9).
2. Внеси мутацию в копию (python-скриптом с `assert old in s` — замена обязана найти шаблон).
3. **Проверь, что мутация применилась, до запуска тестов**: `grep -c '<удалённая строка>' копия`
   → 0, или `diff -r backend/app $SCRATCH/mut` показывает ровно твою правку. Без этой проверки
   «тест прошёл на мутации» может означать, что мутация не применилась (был такой случай).
4. Прогони тест на копии:
   `docker compose --profile test run --rm -v "$SCRATCH/mut:/app/app:ro" tests pytest -k <тест>`.
   Тест обязан упасть. Если проходит — сначала разберись **почему**, и только потом решай:
   - **мутация не там:** сломана строка, которая на этом пути не исполняется (например, ранний
     `return` раньше неё). Найди настоящую защиту и мутируй её;
   - **дублирующие защиты:** одно и то же проверяется в двух местах (условие в подзапросе
     и в самом DELETE; ранний выход и проверка внутри функции очистки). Мутация одной не роняет
     тест — вторая её прикрывает. Мутируй **все** дублирующие места разом: тест обязан упасть.
     Дублирование оставляй осознанно (защита в глубину) и пиши это в отчёте;
   - **тест бесполезен:** ни одно из объяснений не подходит — переписать тест, а не подгонять.
5. Удали копию.

Доложи: какие тесты добавлены, что покрывают, какие мутации проверены и с каким результатом,
что осталось непокрытым.
